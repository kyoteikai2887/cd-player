# 启动与退出修复 · core.13

版本 **0.3.0-r2.2-core.13**，接口保持 **0.3.0**，2026-10-04。

## 这次发生了什么

用户反馈后台关闭后，双击当前和旧版本都没有窗口。实际检查：应用资料目录留有 writer.lock，记录的进程已不存在；library.json 能正常解析。各版本共用同一资料目录，所以遗留锁会同时阻止所有版本启动。原生 release 启动失败原先仅写不可见错误，表现为双击无反应。

已将用户收藏文件额外备份，确认旧锁进程不存在后，把锁改名保留；收藏文件哈希在恢复操作前后相同。随后成功打开原 core.12 窗口。未删除或清空收藏、设置、歌词、封面或原音乐。私有恢复备份只保存在本机，没有放入交付 ZIP。

当时具体退出方式没有记录，不能断言一定是强制结束。进一步回归明确复现了一个可能导致遗留锁的退出路径：未完成的媒体/静态 HTTP 连接使旧服务关闭一直等待，原生 8 秒期限到达后会终止子进程。该用例修复前失败，修复后通过。

## 修复

1. 原生层按规范化资料目录建立 Windows 进程级实例保护，跨版本/会话保持相同标识。进程结束后由系统释放；不会新留下恢复锁文件。实例存在时给出“从托盘恢复”提示，不同时写收藏。
2. 在实例保护范围内，只恢复能够确认进程不存在的资料锁；原锁改名保留，收藏文件不重建。活进程、权限导致的未知状态、无效/空锁及 PID 复用都保守拒绝。普通无实例保护的本地开发入口不自动抢锁。
3. 新资料锁附带随机所有者标记，关闭时不删除替换后的他人锁。关闭 HTTP 服务先停止接收，再结束已有连接、取消文件任务，并等待写入队列完成后释放资料锁。
4. 后端启动失败返回结构化原因；原生壳显示明确提示并保存 last-startup-error.txt。缺少 runtime/web、资料被占用和资料读取失败不再只表现为无窗口。

实例对象生命周期按 [Microsoft CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw) 处理；跨会话命名依据 [Windows kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces)。关闭连接顺序依据 [Node 24 HTTP 服务文档](https://nodejs.org/docs/latest-v24.x/api/http.html#servercloseallconnections)。这些是实现参考，不是本机验收结果。

## 使用

请先从当前播放器托盘菜单“退出”，再将 **CD_Player_R2_2_Windows_Prototype_20261004_fix1.zip** 解压到新目录运行。不要只复制 exe，runtime、web、licenses 需一起保留。已有收藏和设置沿用。

试一下“托盘退出 → 双击重新打开”，以及“收到托盘 → 点击托盘恢复”。正常运行时不要同时打开不同版本；重复打开新版会给出恢复提示。若再出现启动提示，保留提示文字或资料目录的 last-startup-error.txt 供检查，勿删除 library.json。
